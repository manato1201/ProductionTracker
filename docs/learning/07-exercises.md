# 7. 演習と確認問題

## 進め方
1. **ブランチを切る**。1 つの演習 = 1 ブランチ。
2. **受け入れ条件をテストにする**(先に書いて赤にする)→ 直す → 緑にする。
3. 終わったら [04 の変更前チェックリスト](04-recipes.md#変更を出す前のチェックリスト)を通す。
4. 詰まった点は [learning-log.md](../learning-log.md) に残す。

難しさ: ★ = 1 時間以内 / ★★ = 半日 / ★★★ = 1 日以上。**答えの方針**は各演習の末尾(まず見ずに挑戦する)。

---

## 演習 1(★)タスクに「説明」を足す
**目標**: タスクに自由記述の説明を持たせ、ドロワーに表示・編集できるようにする。
**受け入れ条件**
- 作成と PATCH で `description` が往復する(API のテスト)。
- 閲覧者は変更できない(403)。
- ドロワーの詳細に表示される。360px で横スクロールしない。
**ヒント**: [レシピ A](04-recipes.md#a-タスクに項目を足す例-description) そのもの。型チェックが指摘する場所を順に直す。
**答えの方針**: モデル → マイグレーション → シリアライザ → 型 → 表示。

## 演習 2(★)並べ替えに「優先度順」を足す
**目標**: `GET /tasks/?ordering=priority`(緊急 → 高 → 中 → 低)と、概要の「タスク」タブの並べ替えチップ。
**受け入れ条件**
- 緊急・高・中・低の 4 件を作り、`ordering=priority` で緊急が先頭、`-priority` で逆順(API のテスト)。
- 許可リストにない値は 400 のまま。
- チップを押すと並び替わる。
**ヒント**: `TaskViewSet.ORDERING` は許可リスト。優先度は文字列なので、アルファベット順ではなく **`Case` / `When` で数値に写して**並べる。同順位は id で固定される(`apply_ordering`)。
**落とし穴**: `"priority"` をそのまま `order_by` に渡すと「high, low, normal, urgent」順になる。

## 演習 3(★★)状態「保留(blocked)」を足す
**目標**: 進行中 ⇄ 保留 を行き来できる 5 つめの状態。
**受け入れ条件**
- 遷移表の全組み合わせのテストが通る(新しい遷移を `ALLOWED` に足す)。
- かんばんに 5 列目が出る。900px 以上で 5 列が収まり、未満は 1 列。
- 積み上げバー・凡例・自分のタスクに出る。ライト/ダークで読める(4.5:1)。
**ヒント**: [レシピ B](04-recipes.md#b-タスクの状態を-1-つ足す例-保留-blocked)。**サーバーは `models.py` だけ**で、落ちるテストは 4 件のはず。
**答えの方針**: 状態の追加は「表」と「見た目」。ルール(遷移表)をまず決めて、テストを直し、見た目を足す。

## 演習 4(★★)ノートの編集と削除(自分のノートだけ)
**目標**: ノートを書いた本人だけが、編集・削除できる(レビュアーは削除のみ可、など方針を自分で決めて文書化する)。
**受け入れ条件**
- `PATCH /notes/{id}/`・`DELETE /notes/{id}/` を追加。他人のノートは 403、見えないノートは 404。
- UI: 自分のノートに「編集」「削除」。削除前に確認。
**ヒント**: `NoteViewSet` は今 `List` と `Create` だけ。`get_queryset` は **対象を必須にしている**(一覧用)ので、詳細・更新では `visible_*` 経由で引き直す必要がある。方針(誰が消せるか)は `models.py` のメソッドか `permissions.py` に置く。
**落とし穴**: ノートの取得に使う `ContentType` の絞り込みを、更新でも通す(他プロジェクトのノートを書き換えられない)ように。

## 演習 5(★★)プロジェクトのメンバー管理 API と画面
**目標**: 今は管理画面でしか変えられないメンバーを、レビュアーが画面から追加・変更・削除できる。
**受け入れ条件**
- `POST /projects/{id}/members/`・`PATCH`・`DELETE`。**レビュアーだけ**(管理者は可)。
- **最後のレビュアーは消せない / 役割を下げられない**(承認できなくなるため)→ 409。
- 重複して追加できない(400)。
**ヒント**: `ProjectViewSet.members` は今 GET だけ。業務ルール(最後のレビュアーを守る)は **モデルのメソッド**に書き、`DomainError` のサブクラスで投げる。
**落とし穴**: 自分自身の役割を変えるとき、変更後に自分の権限がどうなるか。

## 演習 6(★★)`shot` に対応する
**目標**: アセットと同じ画面で `shot` も扱う。
**受け入れ条件**: [レシピ G](04-recipes.md#g-shotショットに対応する) の 4 点。種別での絞り込み(`?kind=`)が UI から使える。
**答えの方針**: 制限は `validate_kind` の 1 か所だけ。残りは UI。

## 演習 7(★★★)外部 ID 基盤の認証クラスを差し込む
**目標**: `Authorization: Bearer <JWT>` でログインできるようにする(検証は、鍵を環境変数から読む HS256 の簡易版で十分)。
**受け入れ条件**
- 正しい JWT で `/me/` が 200、改ざん・期限切れは 401。
- 既存のセッション・トークン認証は壊れない。
- **ビューと権限のコードを変更していない**(`API_AUTHENTICATION_CLASSES` に足すだけ)。
**ヒント**: [auth.md](../auth.md)。`BaseAuthentication` を継承し、`authenticate_header` を返して **401** にする(返さないと 403 になる。過去にはまった点)。
**落とし穴**: トークンを **ログ・Sentry に出さない**(`tracker/sentry.py` の除去対象に `Authorization` が入っている)。

## 演習 8(★★★)新しい取り込み口(ビルド結果)
**目標**: ビルドツールの結果(`build_id`・成否・所要秒)を、版に紐づけて取り込み、画面に出す。
**受け入れ条件**: [レシピ E](04-recipes.md#e-新しい取り込み口を足す例-ビルド結果) の 7 点(キーなし 401、再送で重複しない、不正入力 400、元データと件数一致、時刻のタイムゾーン必須、図と文書の更新)。

## 演習 9(★)図を直す
**目標**: [システム構成図](../diagrams/architecture.svg)に、演習 8 の「ビルドツール」を足す。
**受け入れ条件**: `docs/diagrams/build.py` を直して再生成。**文字と線が重ならない**(ブラウザで見る)。360px ではなく、README で縮小表示されても読める。
**ヒント**: [diagrams/README.md](../diagrams/README.md)。矢印は折れ線の座標列。終点はグループ枠の縁で止める。

# 確認問題

答えは下。**コードかテストで裏を取ってから**答え合わせをすること。

1. 状態の遷移が許されるかどうかを決めているのは、どのファイルのどの関数か。画面はそれを判断しているか。
2. 「未着手 → 完了」を、レビュアーが API で試すと、何が返るか。
3. アーティストが「レビュー待ち → 完了」を試すと。
4. レビュアーが、版が 1 つも無いタスクを「完了」にしようとすると。それを許すには何を変えるか。
5. `is_staff` のユーザーは、承認できるか。
6. 同じ `Idempotency-Key` で、別のタスクに版を登録すると。
7. 同じ `scan_run_id` で品質を 2 回取り込むと、2 回目は何が返り、DB はどうなるか。
8. すでに `DEMO` があるときに `demo` を作ろうとすると。
9. `X-API-Key` で `GET /api/v1/projects/` を呼ぶと。
10. ノートの対象に `project` を指定すると。
11. DB を止めると `/healthz` は何を返すか。
12. かんばんの「⋮」ボタンは、なぜ `mousedown` を止めているのか。
13. ドロワーで状態を変えたあと、概要の「タスク」タブの一覧を更新するのは何か。
14. `visible_tasks` を使わずに、`Task.objects.all()` から始めたビューは何が悪いか。
15. 取り込みの時刻に、タイムゾーンが無いと。

## 答え
1. `backend/tracker/models.py` の `Task.transition_to`(表は `Task.TRANSITIONS`)。画面は判断しない。拒否されたら元の列へ戻し、サーバーが返した理由を表示するだけ。メニューの候補は `task.next_statuses`。
2. **409** `{"code": "invalid_transition"}`。誰が試しても同じ(遷移表が最初に検査される)。
3. **403** `permission_denied`(承認はレビュアーのみ)。表の検査は通るが、次の権限の検査で止まる。
4. **409** `version_required`。許すには `REQUIRE_VERSION_FOR_COMPLETION=0`。
5. **できない**。`can_review_as` はレビュアーの役割だけを見る。管理者は全プロジェクトを見られ、承認以外は編集できる。
6. **409** `idempotency_conflict`。同じ鍵が同じタスクなら、新規作成せず同じ版を **200** で返す。鍵はユーザーごとに一意。
7. **200**(新規は 201)。`(project, scan_run_id)` の行は **全て置き換わる**ので、件数は増えない。
8. **400** `validation_error`(大文字小文字の違いも同じ扱い)。DB にも `Lower(code)` の一意制約がある。
9. **401**。`X-API-Key` は取り込み API 専用で、画面の API には使えない。
10. **400**。`target_type` は `entity` / `task` / `version` のみ。
11. **503** `{"status": "error", "db": false}`。例外の中身は返さない。
12. dnd-kit の `MouseSensor` は `mousedown` を見る。ボタンの上でマウスを動かすとドラッグが始まってしまうのを防ぐ。`pointerdown` を止めても `mousedown` は届く。
13. `OverviewPage` の `tasksRevision`(ドロワーの `onChanged` で増やす)。更新日時や件数から推測しない。
14. **見えないはずのタスクが見える**(他のプロジェクトのデータが漏れる)。`visible_*` で最初に絞るのが原則。
15. **400**(`AwareDateTimeField`)。黙って補うと、取り込み元と時刻がずれても気づけないため。`send_quality.py` は `--naive-offset` で明示させる。
