# 学習ログ(各スキルで詰まった点)

実装中に実際に引っかかったことの記録。新しいものを上に足す。

## 外部資料(Z32)の指針で点検した(3 回目のレビュー)
OWASP API Top 10 と SQL の指針を、**文書のチェックリストでなく自動テストにした**ら、見落としが数件見つかった。
- **レート制限がログインにしか無かった。** 「全員が認証済みの API」でも、画面のバグ(ループで API を呼ぶ)や悪意のある連打で資源を使い切れる。ユーザーごと・取り込み全体の枠を足した。
- **API の応答がキャッシュされうる。** Cloudflare を前に置くと、認証済みのデータが共有キャッシュに残りうる。`no-store` を全 API 応答に。
- **自由記述に上限が無かった。** 本文の上限(2.5MB)まで `dcc` やコメントを保存できた。項目ごとに上限を決めた。
- **値の種類が 4 つしかない列(`status`)に索引があった。** 効かないうえ、書き込みを遅くする。外した。
- **`iexact` は、LOWER の索引を使わない。** PostgreSQL では `UPPER(code)` で比べる。**関数をかけた列には、同じ関数の索引**。式をそろえた。
- **同じ落とし穴を、もう一度踏んだ。** 新しい認証クラス(Cloudflare Access)で `authenticate_header` を書き忘れ、失敗が 401 でなく 403 になった。テストが見つけたが、**過去に学習ログに書いた同じ内容**。教訓: 書いただけでは繰り返す。**チェックリスト(新しい認証クラスの雛形 = `cf_access.py`)に入れる**。
- 「全エンドポイントは未認証で 401」のテストは、**ルーターから URL を自動で洗い出す**ので、新しいエンドポイントを足した人が何もしなくても対象になる。ただし、実在しない URL(ノートの詳細は無い)を除くために `resolve()` で絞る必要があった。
- SQLite の `EXPLAIN QUERY PLAN` は「索引があるか」を決定的に確かめられる(小さな表でも使う)。PostgreSQL は小さな表では索引を使わないことがあるので、**テストは SQLite で、実データの確認は PostgreSQL で**と分けた。

## 入力を壊しにいくテストで見つけた不具合(2 回目のレビュー)
「正しい入力で動く」の次は「変な入力で 500 にならない」。API の全一覧・詳細・書き込みに、NUL 文字・巨大な整数・不正な JSON・深いネスト・NaN などを機械的に投げた(`tests/test_robustness.py`、約 215 ケース)。
- **PostgreSQL だけで落ちるものがある。** NUL 文字(検索語・URL・JSON の項目)は SQLite では通り、PostgreSQL では `DataError` で 500。SQLite のテストが全部緑でも安心できない。PostgreSQL でも流す。
- **逆に SQLite だけで落ちるものもある。** bigint を超える ID は SQLite が `OverflowError`(500)。PostgreSQL は(Django が)空の結果にする。**どちらの DB でも 400 にそろえた。**
- **同じ値を合算する列は、1 行の上限では足りない。** 同じパスの欠陥数を足し合わせるので、1 行ずつは 32 ビットに収まっても合計が溢れる。列を bigint にした。
- **受け付けない形式は、受け付けない。** DRF の既定はフォーム・multipart も受け付ける。使わない入口は閉じる(415)。
- 入口で 1 回弾けるものはミドルウェアで(URL の NUL)、項目の中身はシリアライザで(JSON の NUL)。個々のビューに書かない。

## レビューで見つけた不具合(リファクタリング後の見直し)
「動いた」と「正しい」は別、という記録。**再現してから直した**ものには ✔ を付けた(修正前のコードでブラウザ操作を再現し、修正後に解消を確認)。
- ✔ **ドロワーで状態を変えても、タスク一覧(タブ)が古いまま。** 再読み込みの合図に「更新日時 + タスク総数」を使っていたが、状態の変更ではどちらも変わらない。合図を「ドロワーで変更があった回数」に変えた。**教訓: 再読み込みの条件を、結果から推測しない。変更を知らせる明示の合図を持つ。**
- ✔ **「⋮」ボタンの上でマウスを動かすと、ドラッグが始まる。** dnd-kit の `MouseSensor` は `mousedown` を見るのに、`pointerdown` だけ止めていた。ポインタイベントとマウスイベントは別物で、前者を止めても後者は届く。
- **ノートが孤児になる。** 対象は `GenericForeignKey` で、DB の外部キーではないため、アセットを消してもノートが残る。`GenericRelation` を足して連鎖削除にした(スキーマ変更なし)。
- **`demo` と `DEMO` が別のプロジェクトになる。** 一意制約を `Lower(code)` にし、DRF は式の制約を検査しないので、API 側でも先に弾いた(でないと 500 になる)。
- **タイムゾーンの無い時刻を黙って補っていた。** DRF の既定は「サーバーの時間帯とみなす」、スクリプトは「UTC とみなす」で、食い違っていた。どちらも黙って補うのをやめ、明示を必須にした。
- **同じスキャン実行の同時再送で一意制約違反(500)になり得る。** 「削除 → 再作成」の間に割り込まれるため。プロジェクトの行をロックして直列化した。
- **権限の判定が 2 か所にあった**(モデルとシリアライザ)。UI に出す `can_write` と、実際の判定がずれる危険があったので、1 つの関数に寄せ、「常に一致する」テストを足した。
- **ログインに試行回数の制限が無かった。** DRF の `ScopedRateThrottle` で 10 回/分にした。
- 本番の既定 `ALLOWED_HOSTS` にテスト用の `testserver` が入っていた。テスト設定へ移した。
- 絞り込みの値(`?status=` など)のタイプミスが「0 件」に見えていた。選択肢にない値は 400 にした。

## Django / DRF
- **未認証が 401 でなく 403 になる。** DRF は認証クラスが `authenticate_header()` を返さないと、未認証・認証失敗を 403 に変える。`SessionAuthentication` を継承して `authenticate_header` を足し、画面側が 401 を見てログイン画面へ戻せるようにした(`tracker/auth.py`)。ログイン用の CSRF だけ検査するクラスでも同じ。
- **`force_authenticate` は認証クラスを素通りする。** 「画面の利用者(セッション)は取り込み API を呼べない」を `force_authenticate` で試すと、認証クラスが動かず 401 でなく 403(権限クラスで拒否)になる。実際のセッションを使う `force_login` で試すのが正しい。
- **`select_for_update` は SQLite では何もしない。** 版番号の連番(タスク行をロック)は PostgreSQL でしか効果を検証できない。テストを SQLite と PostgreSQL 16 の両方で通した(同時実行そのものの負荷試験はしていない)。`(task, number)` の一意制約を最後の砦にしてある。
- **`UniqueConstraint` に `condition=`(鍵が NULL でないときだけ一意)**で、Idempotency-Key を「鍵があるときだけユーザーごとに一意」にできた。NULL を許す一意制約は DB によって扱いが違うので、条件付きにして意図を明示した。
- 遷移ルールをモデルのメソッドに集約すると、API・テスト・(将来の)管理画面が同じルールを通る。**全 4×4 の組み合わせ表を parametrize** でテストしたので、表を変えたら必ずテストが落ちる(設計書の「全遷移の表」のテスト)。

## pytest / factory_boy
- `PostGenerationMethodCall("set_password")` + `skip_postgeneration_save = True` だと、**パスワードが DB に保存されない**。ログインのテストが 401 になり、原因はファクトリだった。`_create` で `create_user` を呼ぶ形にした。
- 設定を `config.settings_test` に分けた。`DJANGO_SECRET_KEY` 未設定でも起動する分岐を本体に入れず、テスト用モジュールで許可する。

## React / React Router
- 画面の状態(開いているタスク)は `?task=ID` に持たせると、共有・戻るボタン・Esc で閉じる、が URL だけで済む。
- 取得フックは「古い応答を捨てる」(連番で判定)だけで、フィルタを素早く切り替えても表示がぶれなかった。TanStack Query は入れていない(規模的に不要と判断。かんばんの先行更新と巻き戻しは自前で数十行)。

## MUI
- **AppBar の z-index がドロワーを覆った。** 固定の AppBar(`zIndex: drawer + 1`)の下に、右から出すタスクのドロワーの上端(題名・閉じるボタン)が隠れていた。スクリーンショットで気づいた。ドロワーを `zIndex: modal` にして解決。
- 狭い幅(360px)で、タスクの行の右端(優先度・状態・期日)が縮まず **374px まで横にはみ出した**。ブラウザで全画面の `scrollWidth` を計測して発覚。行を縦に積む指定を足した。

## Sass
- デザイントークンの出どころを 1 つにするため、`_tokens.scss` に Sass マップで定義 → CSS 変数(`--pt-*`)として出力し、同じ値を `tokens.module.scss` の `:export` で JS(MUI テーマ)にも渡した。ライト/ダークは `data-theme` と `prefers-color-scheme` の両方に対応。
- 色のコントラストは目視でなく計算で確認した(8 色 × 3 背景 × 2 テーマ、全て 4.5:1 以上)。

## Sentry
- **`@sentry/react` v11 に `sendDefaultPii` が無い。** 代わりに `dataCollection`(userInfo / cookies / httpHeaders / httpBodies / urlQueryParams を個別に指定)。型チェックで気づいた。
- Sentry に実際にイベントが届くことは、DSN が無く確認できていない。代わりに、**送信の直前(トランスポート)を差し替えて**、Django の意図的な例外が 1 件捕捉され、Authorization / X-API-Key / Cookie が含まれないことを確認した。React 側は `scrubEvent` を単体テストで確認。

## Vite / TypeScript / Vitest
- `vite.config.ts` で `process.env` を使うと、`@types/node` が無く型エラー。
- fetch のモックで同じ `Response` を 2 回返すと、2 回目に本文が読めない(使い捨て)。`mockImplementation` で毎回作る。
- 並べ替えや絞り込みのチップは、`aria-pressed` を付けるとテストでも画面読み上げでも状態が分かる。

## ドラッグ&ドロップ
- ポインタ操作と、キーボード・タッチの代替操作を**同じ関数(`onMove`)に流す**と、拒否されたときの巻き戻しとトーストが 1 か所で済む。
- ドロップ前に遷移の可否を UI で判断せず、サーバーの 409/403 を信じて戻す(設計書の方針)。そのぶん「どの遷移が可能か」は `next_statuses` でサーバーから受け取る。

## Docker
- この開発環境には Docker のデーモンがなく、`docker compose config` による構文確認までしかできていない。`docker compose up` での起動、DB 停止時の `/healthz`(代わりに PostgreSQL を直接止めて確認済み)は、手元の PC での確認が必要。
