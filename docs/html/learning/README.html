学習資料 ― 保守・拡張できるようになるために

ProductionTracker を 自分で直せる・足せる ようになるための資料です。 先に読むと速い順に並べました。各章の最後に「確認」(手を動かす課題)があります。

基礎から学びたいときは 講義資料 (L00〜L17。Web・Python・DB・Django・React・アルゴリズム・テスト・運用)へ。 この「実践ガイド」は、手順書(レシピ・困ったとき)として使い分けてください。

順 章 目的 目安
1 全体像 何がどこにあるかを言える。用語と 5 つの原則を知る 30 分
2 バックエンドの道案内 1 本のリクエストが通る道を、コードで追える 60 分
3 フロントエンドの道案内 画面・データ取得・かんばんの仕組みを追える 60 分
4 拡張レシピ 項目・状態・API・画面・取り込み口を足す手順 必要なとき
5 テストの書き方 変更に自信を持つ。バグを再現してから直す 40 分
6 困ったとき 症状から原因をたどる 必要なとき
7 演習と確認問題 理解の確認。足場のある練習問題 数時間
8 セキュリティとデータベースの見方 点検をテストにする。401/403/404 の選び方、索引と実行計画 40 分

まず 30 分で動かす

  1. README の「Docker なしで動かす」で、バックエンドとフロントを起動する。
  2. python manage.py seed_demo --password <パスワード> でデモデータを入れ、demo_reviewer でログインする。
  3. かんばんで「進行中」のカードを「完了」へドラッグする。拒否されて元に戻り、理由が出ることを見る。
  4. その 1 回の操作が通る道を、状態遷移の流れ(図)で確認する。
  5. cd backend && pytest -q を実行する(約 12 秒で 877 件。うち約 280 件は、文書内のコードを実際に動かして確かめるテスト)。

読むときの約束

  • コードを開きながら読む。この資料はファイル名と関数名で場所を示す。行番号は書かない(すぐ古くなるため)。
  • 「なぜそうしたか」は decisions.md、「どこで詰まったか」は learning-log.md にある。
  • 図は docs/diagrams/。直すときは build.py を編集して再生成する。
  • 迷ったら、テストが仕様書。backend/tracker/tests/ を読むと、期待する挙動(ステータスコード・エラーコード)が分かる。

資料の保守

コードを変えたら、変えた場所を指している資料も直す。特に次の 3 つは古くなりやすい。

  1. 04-recipes.md の「変更する場所」の一覧(ファイル名・関数名) (新しい API を足したら、security.md の認可の表と、database.md の索引の表も)
  2. docs/er.md(モデル・制約)と docs/integration.md(API の契約)
  3. docs/diagrams/build.py の図(タイルの名前・矢印のラベル)
