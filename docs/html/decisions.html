設計書から外れた点・補った点

  1. 状態の値は英語コード(todo / in_progress / review / done、版は draft / submitted / approved / rejected)。表示名は日本語ラベルで、API は status_label も返す。DB・API の値を日本語にすると将来の連携で扱いにくいため。
  2. プロジェクトを作った人は、そのプロジェクトのレビュアーになる。そうしないと作成者が自分のプロジェクトを編集も承認もできない。他のメンバーの追加は管理画面(/admin/)で行う(設計書にメンバー管理の API・画面は無い)。
  3. is_staff でも承認はできない(レビュアーの役割が要る)。設計書 §3.3「承認できるのは、プロジェクトのレビュアーのみ」を字義どおりに実装した。ただし管理者は全プロジェクトを閲覧でき、承認以外の編集はできる。
  4. 閲覧者(viewer)は書き込み不可(ノートも含む)。設計書は閲覧者のノート可否を定めていない。
  5. ヒントとしての next_statuses をタスクの応答に追加。遷移表(サーバー)の結果を返し、UI が遷移ルールを二重に持たないため。権限や「版が必要」などの追加条件は含まない(最終判断は transition のみ)。
  6. 遷移の検査順: 遷移表 → 権限(403)→ 追加条件(409 version_required)。「未着手 → 完了」は誰が試しても 409。
  7. shot は未実装(kind は残すが、API は asset 以外を 400 で拒否)。設計書「まずは asset のみ」。
  8. 画面の一覧の上限: かんばん・タスク一覧は最大 10 ページ(2,000 件)まで読む。超えたら画面に件数を出す。プロジェクト一覧は 200 件まで。
  9. API の並べ替えは許可リスト。それ以外の ordering は 400。同順位は id で固定(ページ送りがぶれない)。
  10. 取り込み API の鍵が未設定なら、常に 401(fail closed)。
  11. 取り込みの時刻はタイムゾーン付き必須。send_quality.py も、タイムゾーンが無い値は --naive-offset で明示しない限り止まる(黙って UTC にしない)。
  12. プロジェクトコードは大文字小文字を区別せず一意(demo / DEMO で URL・取り込みの指定が曖昧になるのを避ける)。

ASCII モチーフ(設計書 追補 2026-10-27)で決めたこと

設計書は「提案/未実装」で、細部は「UI を作る段階で決める」としていた。次のように決めて実装した。

  • 元資料 ASCII_MOTIF_MAP_2026-10-27.md はこのリポジトリに無く、中身を確認できていない。 設計書の表の「実装系統: B. Grow」の定義も不明なので、「段階が成長する(種 → 芽 → 花 → 実)」という名前どおりの意味で解釈した。元資料と食い違うなら、domain/motif.ts の差し替えで直せる。
  • 上流(stackedlol/ascii-sharks)のコードは使っていない。 設計書(2026-10-30 版)は上流の動作を「確認済み(型検査・ビルド成功、60fps)」としたが、このアプリでは、依存を増やさず、絵とタイマーを自前で書いた(外部依存なし・数十行)。上流の描画負荷の確認は、各プロジェクトへ組み込んだときの負荷が未確認のまま(設計書どおり)。
  • 出す場所は「空の列」だけにした(設計書「動きは空・待機の状態だけ=P8」)。読み込み中のスケルトン、一覧の空状態(プロジェクトなど)には出していない。出したくなったら EmptyState の motif に渡すだけ。
  • 工程の状態との対応は、設計書が「(候補)」としていたので、状態の並び順どおりに 1 対 1(種・芽・花・実)にした。

第4弾の外部資料(Z32)で決めたこと

設計書は「提案(未実装)」。次のように具体化した。

  • 認証は Cloudflare Access(OIDC): 任意の認証クラスとして実装し、既定では無効にした(Access が無い開発環境でも動くように)。ユーザーは自動作成しない(既定)。実 Cloudflare では未検証。
  • 認可はロール別・最小権限: ロール × 操作の一覧をテストにした(security.md)。承認は管理者でもレビュアーの役割が要る。
  • 401 と 403 の使い分け: 未認証は 401、権限なしは 403、見えないものは 404(存在を明かさない)。
  • OWASP API Top 10(2023)を基準にした点検を、自動テストにした(全エンドポイントは未認証で 401 など)。
  • 「レート制限・入力検証は資料の外なので別に設計する」: 3 種類のレート制限(ユーザー / ログイン / 取り込み)、自由記述・JSON の上限、Cache-Control: no-store。値は環境変数。
  • 「自前の Keycloak・cert-manager は要らない」: 入れていない。
  • SQL の指針: database.md。値の種類が少ない status 単独の索引を削除、iexact を索引の式にそろえた、一覧の ORDER BY をテストで強制、主要クエリの実行計画をテストとコマンド(explain_queries)にした。資料は D1(SQLite)向けで MySQL の EXPLAIN 前提の記述があるが、このアプリは PostgreSQL(テストは SQLite)なので、EXPLAIN と EXPLAIN QUERY PLAN の両方を使い分けた。

入力の堅牢性(設計書にない追加)

  • JSON 以外の本文(フォーム・multipart)は受け付けない(415)。 画面もスクリプトも JSON だけを送る。受け付ける形式が少ないほど、検証すべき入口が減る。
  • NUL 文字(\x00)は URL(ミドルウェア)と JSON の項目(シリアライザ)で 400 にする。 PostgreSQL は保存できず、通すと 500 になる(SQLite は通すので、SQLite のテストだけでは気づけない)。
  • bigint を超える ID は 400。 QualityReport.defects は、同じパスを合算するので bigint。
